# Rich Health Care

Production platform for Rich Health Care: PAN registration, issued Member IDs, KYC, PINs, binary matching, wallet ledger, manual UTR payments, and **weekly admin-approved payouts**.

There are **no demo logins**. After an empty database is created, open `/setup` once and save the first distributor password.

## What the client gets

- Join at ₹999 with PAN, optional sponsor ID, optional joining PIN
- Manual UTR for joining and product orders (admin approves; no Razorpay in this phase)
- Matching: ₹250 gross / ₹225 net per pair, 10 pairs/day, GST 5% + admin 5%
- Member wallet, team counts, bank details, weekly payout queue (Monday–Sunday IST)
- Admin: payments, KYC, PINs, weekly payouts, members, products, matching, plan + company bank + public contact

## Local run

Node 20+, PostgreSQL `DATABASE_URL`, and a strong `JWT_SECRET` in `.env` (copy from `.env.example`).

```bash
npm install
npx prisma generate
npx prisma db push
npx tsx prisma/seed.ts
npm run dev
```

Open [http://127.0.0.1:43123](http://127.0.0.1:43123).

- Empty members table → `/setup` (creates `ADMIN` and `RHC0001`)
- Seed only writes the product catalog and plan. It never creates users and never deletes members.

```bash
npm test
```

## Deploy: website on Render, database on Railway

The **website** (pages + API) runs on Render. **Postgres stays on Railway.** Render cannot use Railway’s private URL — paste the Railway **public** `DATABASE_URL`.

**Limits:** Render free web **sleeps after ~15 minutes**. Hobby includes **two custom domains**. Railway Postgres must stay running for the site to work (that is the only Railway service you need).

1. In Railway, open the Postgres service → **Variables** / **Connect** → copy the **public** URL (`*.proxy.rlwy.net`, not the private `*.railway.internal` URL). If it has no `sslmode`, append `?sslmode=require`.
2. Push this repo to GitHub.
3. [Render](https://dashboard.render.com) → **New** → **Blueprint** → this repo. Only the web service is created (no Render database).
4. On that web service → **Environment** → set `DATABASE_URL` to the Railway public URL. Save and wait for a redeploy.
5. Open `https://<service-name>.onrender.com/setup` and create the live admin (`ADMIN`).
6. **Custom domain:** service → **Settings** → **Custom Domains**. At your registrar:
   - Apex (`yourdomain.com`): `A` record to `216.24.57.1`, **or** ALIAS/CNAME flatten to `your-service.onrender.com`
   - `www`: `CNAME` to `your-service.onrender.com`

Do not set `PORT`. Do not create a Render Postgres for this app.

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Railway **public** Postgres URL + `sslmode=require` |
| `JWT_SECRET` | Auto-generated by Blueprint, or 24+ random characters |
| `NODE_ENV` | `production` |
| `API_PORT` | `43124` |
| `NODE_VERSION` | `20` |

If the first deploy fails on memory, the free 512 MB instance is too small for this app.

## Railway-only (optional)

You can also run the website on Railway (`railway.json`) later. For this handover, the live site is Render.

## Client operations (day one)

1. Sign in as `ADMIN` with the password chosen at setup.
2. Plan config: collection bank, contact email/phone, catalog photos.
3. Members pay joining ₹999 to the company account and submit the **UTR** (bank/UPI reference), or consume an unused PIN.
4. Approve payments before matching or retail income is credited.
5. Each week: generate weekly reports, verify bank details, approve payouts (wallet debit `WEEKLY_PAYOUT`).

## Scope notes (be explicit with the client)

- PAN is format-checked only (no live NSDL/Karza call)
- Issued password is shown on screen at register/setup; admin can see it until first login. No SMS gateway.
- KYC is a real workflow but does not block PIN, orders, or matching
- Contact form on the public site does not send email; members use the published desk phone/email
- GST invoicing, TDS, and legal MLM compliance remain the company’s responsibility
- No payment-gateway keys in this phase
